## Frame flow

```text
Camera (unchanged: 512x270, 5 FPS)
  -> lores YUV to BGR -> JPEG -> base64 string
  -> serialCamera Queue -> Gateway -> subscriber Pipe
  -> lightweight LaneDetection receiver -> latest base64 + receive counter
  -> enabled LaneDetection work loop -> ImgCodecMixin -> frame_bgr
```

The mixin preserves the original base64 -> NumPy byte buffer -> OpenCV `imdecode(..., IMREAD_COLOR)` sequence. Strict base64 validation rejects malformed packets; decode exceptions and OpenCV decode failure return `None`. The old logger dependency is removed. The original mixin encoding helper is retained for compatibility.

The receiver never decodes. Under its lock it replaces the newest encoded frame and increments a counter. The main thread snapshots that pair, marks each selected counter as processed before decoding, and skips already processed frames. Frames arriving during decoding replace the retained frame for the next cycle; they do not create a processing backlog.

While disabled, the pipe continues draining and no decoding occurs. On disabled -> enabled, the processed counter synchronizes with the current receive count so a stored frame is skipped and the next newly received frame is awaited. Strict boolean LaneControl validation and safe-stop publication remain intact.

Decoded frames must be NumPy arrays with shape `(270, 512, 3)`. Invalid dimensions are skipped. Decode failures and wrong-shape frames each print only the first error in a consecutive failure episode; their flags reset on recovery. The first successful 512x270 BGR decode prints once per LaneDetection thread lifetime. Processing stops at `frame_bgr`.

## Hardware-free validation

Run with Python, NumPy and OpenCV available:

```text
python validate_phase1.py
python validate_phase2.py
```

Phase 2 also runs Phase 1 regression validation automatically. Both passed on Windows using multiprocessing `spawn`, Python 3.13, NumPy 2.5.3 and OpenCV 5.0.0.

Verified:

- All project source syntax/import checks and original Phase 1 routing/protocol/shutdown assertions.
- A deterministic image with white lines and a colored rectangle survives JPEG/base64 round-trip with expected shape, uint8 dtype and low mean pixel error.
- Malformed base64, non-image bytes, empty and wrong-type inputs return `None` safely.
- Real lane-thread methods skip disabled, stale and duplicate frames, select the newest retained frame, validate shape, reject nonboolean controls, and suppress repeated errors.
- Real Gateway and LaneDetection processes receive synthetic JPEG/base64 frames through queues/pipes and print the first successful decode diagnostic exactly once.
- Two malformed-frame episodes separated by valid input demonstrate recovery in the real LaneDetection process. Processes remain alive throughout. Wrong-size frames sent while disabled, including across restart, are not decoded.
- Every observed LaneActuation is exactly `{"steer": 0, "speed": 0, "valid": False}`; shutdown requires normal joins and exit code zero.

Local `.validation-env/` and `.validation-wheels/` contain ignored validation dependencies, not runtime source. The bundled interpreter lacked SSL support, so official PyPI Windows wheels were downloaded via PowerShell HTTPS and installed offline in that isolated environment. No system interpreter was modified.

## Raspberry Pi checks still required

Physical capture, actual lores YUV format, camera initialization, sustained camera delivery and hardware stop behavior remain untested. On Raspberry Pi OS, use `python3-opencv`, `python3-numpy`, and `python3-picamera2` system packages; a virtual environment may need `--system-site-packages`. Picamera2 was not added as a pip dependency.

No lane image-processing algorithm has been migrated yet.
No steering calculation has been migrated yet.
No non-zero motor command can be generated by LaneDetection in Phase 2.

Phase 2 is complete. Phase 3 has not been started.
